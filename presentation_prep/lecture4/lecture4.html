MLflow tracing

Tracing records what happened during one agent request.

TRACING

Observability for LLMs

OpenTelemetry compatible

Use a common observability model.

Every request

Capture the execution path.

Inputs and outputs

Inspect each important step.

Debugging and cost

Find failures, latency, and token usage.

Tracing turns a black-box response into a sequence we can inspect, including retrieval, tools, model calls, and memory.

TRACING

Anatomy of a trace

Trace info

Experiment ID, status, latency, tags, session ID, and metadata.

Trace data

Spans containing LLM calls, tools, inputs, outputs, and timing.

The trace is the complete request. Spans are the nested operations that explain how the request was completed.

TRACING

Span types for GenAI operations

LLMModel inference
TOOLFunctions, APIs, or MCP tools
RETRIEVERVector search and context retrieval
MEMORYConversation read and write
EMBEDDING / RERANKERRetrieval preparation and ranking

Span types make traces easier to filter and interpret.

TRACING

Using the tracing APIs

@mlflow.trace()
def my_function(...): ...

mlflow.update_current_trace(metadata={...}, tags={...})
with mlflow.start_span("step", span_type=SpanType.TOOL): ...
mlflow.search_traces(filter_string="tags.git_sha = '...'")

Use the decorator for simple functions, update_current_trace for metadata, start_span for manual control, and search_traces for analysis.

CODE

Basic tracing

@mlflow.trace(span_type=SpanType.TOOL)
def search_database(query: str) -> list:
    return run_search(query)

result = search_database("transformers")
The function call creates a trace span automatically.

This is the smallest useful example: the function call, inputs, outputs, and failures become visible in MLflow.

TRACING

Adding custom metadata

mlflow.update_current_trace(
    metadata={"session": session_id, "request_id": request_id},
    tags={"git_sha": git_sha, "model_version": "local"}
)

Metadata describes the request. Tags help group traces across versions, environments, and deployments.

AGENT DEVELOPMENT

Custom agent with ResponsesAgent

ResponsesAgent

MLflow contract for prediction, responses, and streaming events.

Existing integrations

Reuse pgvector search, MCP tools, model services, and optional Lakebase memory.

The agent coordinates components from Lectures 2 and 3.

We are not rebuilding retrieval or MCP. The custom agent wraps those capabilities in an MLflow-compatible interface.

AGENT DEVELOPMENT

Core agent methods

get_tool_specsReturns tool definitions for the model.
execute_toolRuns a selected local or MCP tool.
call_llmCalls the model service through AI Gateway.
handle_tool_callProcesses arguments and returns tool output.
load / save memoryReads and writes conversation state.

Separating these responsibilities makes the agent easier to trace, test, and change.

AGENT DEVELOPMENT

The agent loop

system prompt + memory + user request
        ↓
model response or function call
        ↓
execute tool and append result
        ↓
repeat until final response

The loop builds history, calls the model, executes requested tools, repeats, and saves the new conversation.

AGENT DEVELOPMENT

Prediction and streaming

predict()

Synchronous interface returning the completed response.

predict_stream()

Yields events incrementally for real-time delivery.

Both interfaces use the same loop. The difference is whether the caller waits for the final response or consumes events as they arrive.

AGENT DEVELOPMENT

Testing your agent

  1. Load project configuration.
  2. Initialize the agent with model, tools, and memory.
  3. Call predict twice with one session ID.
  4. Check memory persistence.
  5. Inspect the MLflow trace.

A useful test verifies tool use, memory, and trace quality, not only the final text.

Evaluation

Tracing tells us what happened. Evaluation tells us whether the result was good enough.

EVALUATION

Evaluation in LLMOps

Pre-deployment

Test before release.

Within-agent

Use guardrails during execution.

Post-deployment

Evaluate live inputs, outputs, and traces.

Evaluation is continuous: before release, during execution when guardrails are needed, and after deployment.

EVALUATION

Evaluation is an iterative loop

  1. Create a small, high-quality test set.
  2. Run the current agent.
  3. Review results with experts.
  4. Identify error patterns.
  5. Choose metrics and improve.
  6. Expand the set with new failures.

Ten to twenty strong examples are more useful than many vague examples. Evaluation should improve the system.

EVALUATION

Evaluation principles

Requirements to tests

Translate product requirements into observable behavior.

Expert agreement

Experts should agree on pass or fail.

Balanced behavior

Test desired and undesired outcomes.

Explain failures

Record why a case failed.

Good criteria are specific enough for consistent application. Include negative cases and document disagreements.

EVALUATION

Metrics and graders

Code-basedFast, deterministic checks.
Model-basedFlexible LLM judges.
HumanNuanced and authoritative, but slower.
A metric is the behavior. A scorer is how we measure it.

Use code for objective checks, judges for nuance, and humans for calibration and high-stakes decisions.

MLflow GenAI
evaluation

MLflow provides a common interface around test data, prediction functions, scorers, and results.

MLFLOW EVALUATION

Predefined scorers

Single-turn

Relevance, correctness, completeness, fluency, safety, and equivalence.

Trace and session

Groundedness, retrieval relevance, tool-call correctness, completeness, retention, and frustration.

Scorers can evaluate one response or the complete trace and conversation.

MLFLOW EVALUATION

Custom scorers

Guidelines

Natural-language rules for pass or fail feedback.

Template-based judge

Custom instructions with inputs and outputs for scores or structured feedback.

Guidelines are quick for basic standards. Template judges support richer reasoning and numeric scores.

CODE

Guidelines scorer

polite = Guidelines(
    name="polite_tone",
    guidelines=["Use a professional, helpful tone"],
    model="databricks:/course_ops.gateway.chat"
)
mlflow.genai.evaluate(data=test_data, scorers=[polite])

A guideline states a behavior in natural language and MLflow reports whether each response meets it.

CODE

Template-based scorer

quality = make_judge(
    name="response_quality",
    instructions="Score the output for the question from 1 to 5.",
    model="databricks:/course_ops.gateway.chat",
    feedback_value_type=int
)

A judge compares output with input and returns a richer score. Define the scale clearly.

EVALUATION

Aligning judges with human feedback

  1. Collect human feedback in MLflow.
  2. Use examples with human and automated scores.
  3. Apply SIMBA to improve alignment.
  4. Validate on new traces.

An LLM judge can be biased or inconsistent. Human feedback calibrates it to the quality standard we care about.

EVALUATION

Agent-as-a-judge

A judge can inspect the complete trace, not only the final answer.

Trace context

Inspect metadata, spans, tools, and timing.

Questions

Was a tool redundant? Did retrieval support the answer? Where did latency increase?

Trace-aware judges evaluate the process as well as the response.

EVALUATION

Code-based scorers

@mlflow.genai.scorer
def word_count_check(outputs) -> bool:
    return len(str(outputs).split()) < 350

Code scorers are deterministic and fast for word limits, required fields, valid JSON, and citation presence.

MLFLOW LIFECYCLE

Evaluate, log, register

  1. Create eval_inputs.txt.
  2. Define code and model scorers.
  3. Run MLflow GenAI evaluation.
  4. Review failures and metrics.
  5. Log the agent.
  6. Register the model in Unity Catalog.

This is the workflow implemented in Notebook 4.4. We evaluate before registration.

PACKAGING

Logging agents as code

with mlflow.start_run():
    model_info = mlflow.pyfunc.log_model(
        name="agent",
        python_model=agent,
        resources=resources,
        model_config=model_config
    )

Logging packages the agent, configuration, and declared resources. A code-file approach requires set_model inside that file.

PACKAGING

Registering the agent

registered = mlflow.register_model(
    model_uri=model_info.model_uri,
    name="llmops_dev.arxiv.arxiv_agent",
    tags={"git_sha": git_sha}
)
client.set_registered_model_alias(
    name=model_name, alias="latest-model",
    version=registered.version
)

Registration creates a governed Unity Catalog model version. Tags connect it to source, and an alias gives downstream users a stable reference.
