Calling the course model service

OpenAI Python client, authenticated with Databricks

import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DATABRICKS_TOKEN"],
    base_url=f"{WORKSPACE_URL.rstrip('/')}/ai-gateway/mlflow/v1",
)
response = client.responses.create(
    model="course_ops.gateway.chat",
    max_output_tokens=256,
    input="What is Databricks?",
)
print(response.output_text)

Set WORKSPACE_URL and supply DATABRICKS_TOKEN securely before running. Supported API features depend on the destination.

Code adapted from the user-provided working gateway example. The Databricks token is not an OpenAI API key. The OpenAI client does not automatically read a Databricks CLI profile. Sizing provisioned throughput

Workload estimate, supported allocation, then performance testing

01 / Describe demand

Example: 60 requests/min, each with 2,000 input and 300 output tokens.

120,000 input + 18,000 output tokens/min

02 / Check supported capacity

Notebook 1.2 checks GPT OSS 120B eligibility and reads model_unit_chunk_size from the optimization API.

03 / Allocate and estimate cost

The lab sets CAPACITY_CHUNKS = 2, allocates 2 × chunk size, and estimates DBUs for that allocation.

04 / Validate under load

Test realistic traffic against a response-time target. Measure latency and errors, then adjust capacity and retest.

Two chunks are a lab setting, not a sizing recommendation. Notebook 1.2 demonstrates deployment and inference, not load testing.

How do we decide how much capacity our application needs? Start with the traffic we expect. Imagine 60 requests per minute, each averaging 2,000 input tokens and 300 output tokens. That gives us 120,000 input tokens and 18,000 output tokens per minute. I am keeping those separate because processing input and generating output place different demands on the model. This is an illustrative workload, not a benchmark result from our notebook.

Now look at what notebook 1.2 actually does. For GPT OSS 120B, it asks the optimization API whether the model is eligible and what allocation increment it supports. That increment is model_unit_chunk_size. Think of it as the size of one block of capacity we can allocate. It does not tell us how many blocks our workload needs.

The notebook chooses two blocks with CAPACITY_CHUNKS set to two. It multiplies that value by the returned chunk size and passes the result as provisioned_model_units. It also estimates the hourly DBUs for that allocation. Two chunks do not mean two model units, and they do not mean we have proven this is enough for our example traffic. Likewise, the separate 50-unit cost example explains billing arithmetic, not workload sizing.

The missing production step is validation. We would agree on an acceptable response time, run realistic requests at the expected concurrency, and measure latency and errors. Then we would adjust capacity and repeat the test. The notebook makes a demonstration inference call, so it does not perform that load test for us. Also, changing CAPACITY_CHUNKS and rerunning creation will not resize an existing endpoint: the lab deliberately stops when the endpoint name already exists.

The takeaway is that traffic estimates describe demand, the API tells us valid allocation increments, and performance testing tells us whether our chosen allocation is enough. Allocated on-demand capacity continues to cost money while idle, so cleanup remains part of the lab.

References: notebook 1.2, sections 2–4 and 6; on-demand deployment; model units.
