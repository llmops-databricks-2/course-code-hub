01

Databricks as a platform

Who runs what, and where

DATABRICKS AS A PLATFORM

Your Databricks account, and your cloud account

Your Databricks account (run by Databricks)
Your cloud account
Control plane
Web application, REST APIs, jobs, Unity Catalog, small notebook results
Nothing: the control plane is always Databricks'
Compute plane
Serverless: notebooks, jobs, SQL warehouses, model serving, apps. The course uses only this
Classic: clusters in your VPC, no public IPs, connecting out to the control plane
Storage
Default storage of a serverless workspace: tables, volumes, the workspace's own files
Your S3 bucket: workspace storage of a classic workspace, external data

Two separate perimeters, as in Databricks' architecture picture; users and applications come in from outside. The course: express setup, a serverless workspace on AWS us-west-2, so everything is in your Databricks account and you have no cloud account.

The control plane is Databricks' backend: the web application and the services behind it, run by Databricks in your Databricks account, outside your cloud account. The compute plane is where data is processed. Serverless compute runs in Databricks' account, in the same region; classic compute runs in the customer's account and connects out through secure cluster connectivity, with no open ports and no public IPs. A serverless workspace, which is what express setup gives you, uses only serverless compute and default storage. Traffic between the control plane and serverless compute stays on the cloud backbone. To show Databricks' own picture, open the architecture diagram on the high-level architecture page (first source) live.

DATABRICKS AS A PLATFORM

Results come home two ways

Small result

Notebook results that are small stay in the control plane and are shown in your browser.

Large result

Larger notebook results, and every job's results, are written to the workspace storage.

Cloud Fetch

Above 1 MB, a SQL client gets presigned URLs and downloads Arrow files straight from storage, in parallel.

Where results live matters for governance: in a classic workspace that storage is a bucket in your account.

Cloud Fetch applies to query results larger than 1 MB; files are up to 20 MB each and are cleaned up after about two days. The Python SQL connector uses Cloud Fetch by default and needs PyArrow.

ACCOUNT AND IDENTITIES

Four admin roles, four scopes

RoleScope and typical tasks
Account adminWorkspaces, metastores, users, service principals, account groups, federation policies. Only account admins create workspaces
Billing adminBudgets and serverless usage policies

Some objects must exist before any automation can run: its own identity, roles, groups, catalogs.

SECRETS

Three places for a secret

WhereHow it works
Workspace secret scopeOne workspace; ACL per scope (READ, WRITE, MANAGE): who reads one secret reads all. 1,000 scopes, 128 KB a value
Azure Key Vault-backed scopeAzure only; a read-only window on a vault you manage in Azure. Access policies, not RBAC; the scope exposes the whole vault
Unity Catalog secretcatalog.schema.secret in every workspace on the metastore; READ SECRET per secret; reads audited; 60 KiB
On AWS and Azure a Unity Catalog schema can also front AWS Secrets Manager or Key Vault (Beta).

Creating a scope: databricks secrets create-scope; reading: dbutils.secrets.get(scope=, key=), redacted in output. UC: databricks secrets-uc create-secret, dbutils.secrets.get(catalog=, schema=, key=). The course keeps its few secrets in course_ops.secrets.

MANAGING RESOURCES

The ensure pattern makes imperative code safe

def ensure_volume(w, catalog, schema, name, comment):
    full_name = f"{catalog}.{schema}.{name}"
    try:
        volume = w.volumes.read(full_name)
    except NotFound:
        w.volumes.create(catalog_name=catalog,
                         schema_name=schema, name=name,
                         volume_type=VolumeType.MANAGED,
                         comment=comment)
        return StepResult("created", full_name)
    if volume.comment != comment:   # drift
        w.volumes.update(full_name, comment=comment)
        return StepResult("updated", full_name)
    return StepResult("adopted", full_name)

Look up by name

The deterministic name is the key; no state file to lose.

Create only when missing

A second run changes nothing.

Report what happened

created, adopted, updated: the run's audit trail.

This is the shape of every onboarding step in course-assistant. The SDK is used there because the run loops over a student list from a sheet, calls GitHub in the same run, and records each step in a table: the list is the desired state, the audit table is the state.

A LOST WORKSPACE

2 November 2026

WhenWhat happened
10:09 UTCCompute blocked after a payment-method update: every query and model call refused
14:46 UTCThe API answers "Workspace … has been banned"
Same dayA new express setup workspace in a second account; the repository points at it
ThenSetup script, cohort tables, GitHub variables; onboarding in narrowing runs: teachers' projects, a dry run, one test student, everyone
Student repositories survived: they live in GitHub. The onboarding gave them new principals and variables.

What did not come back was data no code makes: tables and traces written in the old workspace, which no compute could read while it was blocked. Runbook: course-assistant docs/RUNBOOK.md, A new workspace.

A LOST WORKSPACE

What comes back, and what does not

Made by code

Users, schemas, grants, warehouses, principals, jobs, apps: rebuilt by running the code again

Made by a job

Tables a pipeline writes: rebuilt by re-running it, if the source still exists

Made by hand, or history

Uncommitted notebooks, clicked objects, traces: gone. That is what backups are for

Databricks' DR guidance: treat every workspace artifact as infrastructure as code. There is no one-click move.

The Terraform exporter can capture an existing workspace's configuration but is experimental, and does not cover MLflow data or secrets. Demo: inventory.py lists what you own and what your bundle declares.
