From PDF to vectors: how text is prepared for vector search

A language model cannot read a whole library for every question. So the library is cut into small passages, each passage is turned into a list of numbers that captures its meaning, and at question time the system finds the passages whose numbers are closest to the question's. This page walks through each step with three short sample papers you can cut, embed and search yourself, or with your own text: every step has the same text box, and an edit in any of them changes the text on the whole page.

The three sample papers were written for this page. The tokenizer and the embedding on this page are small illustrations that run in your browser; the real ones are named at each step.

5Tokens: the unit models count in

Models do not read characters or words. A tokenizer splits text into tokens: common words stay whole, rare and long words break into pieces. Every limit in this pipeline is counted in tokens: the embedding model's window, the chunk size, the context budget of the prompt. A rough rule for English is four characters per token.

4Chunking: cutting documents into passages

One vector per paper would blur every topic of the paper into one point. One vector per sentence would lose the context around it. Chunking picks the middle: passages small enough that each vector means one thing, large enough to carry their own context. Change the strategy and the sizes and watch the chunks change.

Blank lines separate paragraphs; a short line without a full stop starts a section. Your own text is chunked live and joins the three sample papers in the search below.

678Embed, store and search

An embedding model reads a chunk and returns a fixed-length list of numbers, its vector: 1,024 numbers for GTE-large-en-v1.5. Chunks about the same thing get vectors that point in similar directions, even when they use different words. At question time the question is embedded with the same model, and the store returns the chunks whose vectors are closest, measured by cosine similarity.

The embedding here is a toy you can see inside: it counts words, and a small hand-made list groups words with the same meaning (passage and chunk, find and retrieve). A real model learns those relations from billions of sentences, and its 1,024 numbers do not stand for individual words.

Results

Two stages: retrieve many, rerank, keep a few

Vector search is fast because every chunk's vector was computed in advance: at question time it only measures distances. But a distance between two separately made vectors is a rough guess at relevance. So the search returns more candidates than needed, and a reranker reads the question and each candidate together, scores how well that passage answers that question, and keeps the best k. It is slower, a model call per candidate, which is why it only sees the N candidates and never the whole store. In the course, notebook 2.4 runs similarity_search, then DatabricksReranker.

The reranker here is a toy you can see inside: it scores how much of the question a passage covers, rare question words weighing more, a word as written more than one of the same meaning, and the best single sentence most. A real reranker is a cross-encoder, a model that reads both texts in one pass.

      Where each step lives

      The lecture (notebooks 2.2 to 2.4)

      • PDFs from the arxiv package into a Unity Catalog volume, metadata into arxiv_papers, only papers not yet processed.
      • ai_parse_document over READ_FILES(…, format => 'binaryFile') into ai_parsed_docs.
      • Cleaned chunks with their metadata into arxiv_chunks, Change Data Feed on.
      • A Delta Sync index with managed embeddings, databricks-gte-large-en, TRIGGERED, then similarity_search with filters, hybrid search and a reranker.

      Practices the course checks

      • Process incrementally, one parse per file; PDFs stay in the volume, never in a Delta table.
      • Every chunk keeps paper_id, title, authors and the date, for filters and reranking, and a unique id.
      • Query and documents are embedded by the same model, called through the gateway (course_ops.gateway.embed).
      • Measure retrieval before changing it: a small test set, then recall@k and precision@k.
      • Never create your own Vector Search endpoint: one bills by the hour whether it is used or not.
